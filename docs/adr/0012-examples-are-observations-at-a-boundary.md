# ADR-0012 · An example is an observation at a boundary, compared outside the subject's process

**Status:** accepted

## Context

If the expected value of a hidden check sits in the same process as the code under test, that
code can read it or make the comparison succeed. Two of the four measured cheating techniques
(overloading comparison operators, keeping state between calls) work that way.

## Decision

- An example is a list of steps at a declared boundary: `function`, `cli` or `http`. Each step has
  an input and what is expected to be observed.
- The code under test receives **only the inputs**. It returns an observation serialised as JSON.
  The comparison with the expected value happens in the harness, outside the verification zone.
- Comparison is exact, except for a **closed catalogue** of matchers (any identifier, any
  timestamp, approximate number, unordered collection, contains, pattern, reference to an earlier
  step). Examples contain no code. The catalogue grows only by ADR.
- Each example runs in a new process.

## Basis

Reasoning, driven by the techniques classified in
[ImpossibleBench](https://arxiv.org/abs/2510.20270). No study was found that measures this design.

## Alternatives considered

- **Hidden tests mounted read-only next to the code under test.** The code can read them while it
  is being examined.
- **Tests generated by a model from the examples.** The step from an approved example to a check
  would be written by a model.

## Consequences

- The kernel compares JSON and knows no language. `cli` and `http` need nothing per language;
  `function` needs a small probe in the language pack.
- It does not express graphical interfaces, concurrency or performance.
- Matchers and step references are a small language inside the files. They stay acceptable only
  while the catalogue is closed.
